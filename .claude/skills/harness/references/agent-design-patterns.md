# 에이전트 설계 패턴 레퍼런스

## 1. 실행 모드

하네스에서 에이전트를 실행하는 두 가지 모드가 있다.

### 1.1 에이전트 팀 모드 (Agent Team)

```
Orchestrator (skill)
    |
    +-- TeamCreate --> Agent A (독립 스레드)
    +-- TeamCreate --> Agent B (독립 스레드)
    +-- TeamCreate --> Agent C (독립 스레드)
    |
    +-- SendMessage(A, "작업 지시")
    +-- SendMessage(B, "작업 지시")
    +-- SendMessage(C, "작업 지시")
    |
    +-- [각 에이전트가 결과를 반환]
    +-- Orchestrator가 결과 종합
```

**도구**: `TeamCreate`, `SendMessage`, `TaskCreate`/`TaskStop`

**특성**:
- 각 에이전트가 독립 스레드에서 실행
- 에이전트 간 직접 메시지 교환 가능
- Orchestrator가 중앙에서 조율
- 에이전트 상태 추적 가능
- 긴 수명의 작업에 적합

**제약**:
- 설정 복잡도 높음
- 에이전트 간 컨텍스트 공유가 메시지 기반으로 제한
- 에이전트 수에 비례해 토큰 소비 증가

### 1.2 서브 에이전트 모드 (Sub-Agent)

```
Orchestrator (skill)
    |
    +-- Agent(prompt="작업 A") --> 결과 A
    +-- Agent(prompt="작업 B") --> 결과 B
    +-- Agent(prompt="작업 C") --> 결과 C
    |
    +-- Orchestrator가 결과 종합
```

**도구**: `Agent` tool

**특성**:
- 단일 도구 호출로 에이전트 생성 + 작업 지시 + 결과 수신
- 부모가 프롬프트를 완전히 제어
- 에이전트 간 통신 불가 (부모를 통해서만 가능)
- `run_in_background: true`로 병렬 실행 가능
- `isolation: "worktree"`로 독립 작업 환경 제공

**제약**:
- 에이전트 간 직접 메시지 교환 불가
- 한 번 실행 후 종료 (재사용 불가)
- 결과가 부모 컨텍스트로만 반환

### 1.3 모드 비교

| 기준 | 에이전트 팀 | 서브 에이전트 |
|------|-----------|------------|
| 에이전트 간 통신 | 직접 가능 | 부모 경유만 |
| 에이전트 수명 | 지속 | 일회성 |
| 설정 복잡도 | 높음 | 낮음 |
| 병렬 실행 | TeamCreate로 | run_in_background로 |
| 작업 환경 격리 | 별도 관리 필요 | worktree 자동 제공 |
| 적합 시나리오 | 토론, 반복 협업 | 독립 작업 위임 |

## 2. 모드 선택 의사결정 트리

```
에이전트가 서로 대화해야 하는가?
├─ YES --> 에이전트 팀 모드
│         에이전트 수가 4개 이상인가?
│         ├─ YES --> 감독자 패턴 검토
│         └─ NO  --> 기본 팀 모드
└─ NO  --> 작업이 독립적으로 분할 가능한가?
          ├─ YES --> 서브 에이전트 모드
          │         병렬 실행이 필요한가?
          │         ├─ YES --> run_in_background: true
          │         └─ NO  --> run_in_background: false
          └─ NO  --> 단일 에이전트 (스킬 내 직접 처리)
```

## 3. 6가지 아키텍처 패턴

### 3.1 파이프라인 (Pipeline)

```
[Stage 1] --> [Stage 2] --> [Stage 3] --> [최종 결과]
```

**용도**: 순차적 변환이 필요한 작업. 각 단계의 출력이 다음 단계의 입력.
**예시**: 번역 -> 교정 -> 포맷팅, 데이터 수집 -> 분석 -> 시각화
**구현**: 서브 에이전트를 순차 호출. 각 에이전트의 결과를 다음 프롬프트에 포함.

```
result_1 = Agent(prompt="1단계: 원문 분석...")
result_2 = Agent(prompt="2단계: {result_1} 기반으로 변환...")
result_3 = Agent(prompt="3단계: {result_2} 기반으로 최종 검수...")
```

**장점**: 단순하고 예측 가능. 각 단계 독립 테스트 가능.
**단점**: 지연 시간이 단계 수에 비례. 한 단계 실패 시 전체 중단.

### 3.2 팬아웃/팬인 (Fan-out/Fan-in)

```
                +-- [Worker A] --+
                |                |
[Orchestrator] -+-- [Worker B] --+--> [Aggregator]
                |                |
                +-- [Worker C] --+
```

**용도**: 동일한 유형의 독립 작업을 병렬 처리 후 결과 병합.
**예시**: 다중 소스 리서치, 병렬 코드 검사, 다관점 분석
**구현**: 서브 에이전트를 `run_in_background: true`로 동시 실행.

**장점**: 처리 시간 단축. 확장성 우수.
**단점**: 결과 병합 로직이 필요. 결과 품질 편차 가능.

### 3.3 전문가 풀 (Expert Pool)

```
[Router] --> 작업 유형 판별
    |
    +-- 유형 A --> [Expert A]
    +-- 유형 B --> [Expert B]
    +-- 유형 C --> [Expert C]
```

**용도**: 작업 유형에 따라 전문화된 에이전트에 라우팅.
**예시**: 언어별 코드 리뷰, 도메인별 질문 응답
**구현**: Orchestrator가 입력을 분류한 뒤 적합한 서브 에이전트/에이전트 타입에 위임.

**장점**: 전문성 극대화. 프롬프트를 도메인에 최적화 가능.
**단점**: 라우팅 오류 시 부적합한 전문가에 배정. 전문가 정의 유지보수 비용.

### 3.4 생성-검증 (Generate-Verify)

```
[Generator] --> 산출물 --> [Verifier] --> 통과?
                              |
                              +-- NO --> [Generator] (재생성)
                              +-- YES --> 최종 결과
```

**용도**: 품질 보증이 중요한 산출물 생성.
**예시**: 코드 생성 + 테스트, 콘텐츠 생성 + 사실 확인, 디자인 + QA
**구현**: Generator와 Verifier를 별도 에이전트로 분리. 루프 실행.

**장점**: 자동 품질 관리. 반복으로 품질 수렴.
**단점**: 수렴하지 않을 위험. 최대 반복 횟수 제한 필요.

### 3.5 감독자 (Supervisor)

```
[Supervisor]
    |
    +-- 작업 분배 --> [Worker A]
    +-- 작업 분배 --> [Worker B]
    +-- 진행 상태 모니터링
    +-- 실패 시 재배정
    +-- 결과 검증 및 종합
```

**용도**: 복잡한 프로젝트에서 다수의 워커를 동적으로 관리.
**예시**: 대규모 코드 마이그레이션, 다단계 데이터 처리
**구현**: 에이전트 팀 모드. Supervisor가 SendMessage로 작업 지시 및 상태 확인.

**장점**: 동적 작업 재배정. 실패 복구 가능.
**단점**: Supervisor의 컨텍스트 윈도우 부담. 설계 복잡도 높음.

### 3.6 계층적 위임 (Hierarchical Delegation)

```
[Top-level Orchestrator]
    |
    +-- [Mid-level Orchestrator A]
    |       +-- [Worker A1]
    |       +-- [Worker A2]
    |
    +-- [Mid-level Orchestrator B]
            +-- [Worker B1]
            +-- [Worker B2]
```

**용도**: 대규모 작업을 계층적으로 분해.
**예시**: 전체 시스템 리팩토링, 다모듈 프로젝트 생성
**구현**: Orchestrator 스킬이 하위 Orchestrator 스킬을 호출.

**장점**: 관심사 분리. 각 계층이 관리 가능한 규모.
**단점**: 깊은 계층은 지연과 토큰 비용 증가. 3단계 이상은 권장하지 않음.

## 4. 복합 패턴

실제 프로젝트에서는 단일 패턴보다 복합 패턴이 일반적이다.

### 파이프라인 + 팬아웃/팬인
```
[수집 단계] --> 팬아웃 [분석 A, B, C] --> 팬인 --> [종합 단계]
```
리서치처럼 수집-분석-종합이 순차이지만 분석은 병렬.

### 생성-검증 + 전문가 풀
```
[Generator] --> [Router] --> [Domain Verifier A or B] --> 피드백 --> [Generator]
```
생성물의 유형에 따라 다른 검증 전문가가 검토.

### 감독자 + 파이프라인
```
[Supervisor] --> [Pipeline Stage 1 Team] --> [Pipeline Stage 2 Team]
```
각 파이프라인 단계를 감독자가 관리.

## 5. 에이전트 타입 선택

### 5.1 빌트인 에이전트 타입

| 타입 | 설명 | 도구 | 적합 용도 |
|------|------|------|----------|
| `general-purpose` | 범용 에이전트 | 모든 도구 | 코드 수정, 파일 생성, 복합 작업 |
| `Explore` | 읽기 전용 탐색 | Glob, Grep, Read 등 (쓰기 불가) | 코드 검색, 심볼 찾기, 파일 탐색 |
| `Plan` | 설계 및 계획 | 읽기 도구 (쓰기 불가) | 구현 계획, 아키텍처 설계 |

### 5.2 빌트인 타입 선택 기준

```
에이전트가 파일을 수정해야 하는가?
├─ YES --> general-purpose
└─ NO  --> 정보 탐색만 필요한가?
          ├─ YES --> Explore (빠르고 가벼움)
          └─ NO  --> 설계/계획이 필요한가?
                    ├─ YES --> Plan
                    └─ NO  --> general-purpose
```

### 5.3 커스텀 에이전트 타입

`.claude/agents/` 디렉토리에 마크다운 파일로 정의한다.

## 6. 에이전트 정의 구조

```markdown
---
model: sonnet               # 사용 모델 (sonnet, opus, haiku)
allowed_tools:               # 허용 도구 목록
  - Read
  - Grep
  - Glob
  - Agent                    # 하위 에이전트 생성 허용 시
  - "mcp__github__*"         # MCP 도구 와일드카드
tool_permissions:            # 도구 권한 설정
  allow:
    - "Bash(npm test:*)"     # 패턴 기반 허용
---

# 에이전트 이름

## 역할
이 에이전트의 역할을 명확히 기술한다.

## 작업 범위
- 수행하는 작업
- 수행하지 않는 작업

## 출력 형식
결과를 어떤 형식으로 반환할지 정의한다.

## 작업 절차
1. 단계별 절차를 기술한다
2. 판단 기준을 명시한다
3. 에러 처리 방법을 포함한다
```

## 7. 에이전트 분리 기준

에이전트를 분리할지 판단하는 4가지 기준:

### 7.1 전문성 (Specialization)
프롬프트가 400줄 이상이거나 도메인 지식이 깊다면 분리한다. 단일 에이전트에 모든 전문성을 넣으면 지시 충돌이 발생한다.

**분리 신호**: "이 에이전트가 A도 하고 B도 하고 C도 해야 한다" -> 분리 대상

### 7.2 병렬성 (Parallelism)
독립적으로 동시 실행 가능한 작업이 있다면 분리한다. 병렬 실행으로 총 소요 시간을 줄일 수 있다.

**분리 신호**: "A 작업을 기다리지 않아도 B를 시작할 수 있다" -> 분리 대상

### 7.3 컨텍스트 (Context)
서로 다른 파일/데이터/도구가 필요한 작업은 분리한다. 하나의 컨텍스트 윈도우에 모든 정보를 담으면 성능이 저하된다.

**분리 신호**: "이 에이전트가 100개 파일을 전부 읽어야 한다" -> 팬아웃으로 분리

### 7.4 재사용성 (Reusability)
여러 스킬/워크플로우에서 반복적으로 필요한 작업은 독립 에이전트로 분리한다.

**분리 신호**: "이 작업을 다른 스킬에서도 쓸 수 있다" -> 커스텀 에이전트 타입으로

## 8. 에이전트 재사용 설계

### 8.1 커스텀 에이전트 타입으로 정의

반복 사용되는 에이전트는 `.claude/agents/`에 정의한다.

```
.claude/agents/
    researcher.md        # 리서치 전문 에이전트
    code-reviewer.md     # 코드 리뷰 전문 에이전트
    qa-checker.md        # QA 검증 에이전트
```

### 8.2 프롬프트 템플릿화

에이전트 프롬프트에서 변동 부분을 파라미터로 추출한다.

```
# 나쁜 예
Agent(prompt="React 코드를 리뷰해줘. src/App.tsx 파일을 봐줘.")

# 좋은 예
Agent(
    subagent_type="code-reviewer",
    prompt=f"다음 파일을 리뷰해줘: {target_files}. 기준: {review_criteria}"
)
```

### 8.3 인터페이스 표준화

에이전트 간 데이터 교환 형식을 표준화한다. JSON 스키마를 정의하고 모든 에이전트가 동일한 형식으로 입출력한다.

## 9. 스킬 vs 에이전트 구분

| 기준 | 스킬 | 에이전트 |
|------|------|---------|
| 실행 주체 | 현재 대화 컨텍스트 | 별도 컨텍스트 |
| 정의 위치 | `.claude/skills/` | `.claude/agents/` |
| 컨텍스트 | 부모 대화와 공유 | 독립 컨텍스트 |
| 용도 | 지시/가이드/패턴 제공 | 독립 작업 수행 |
| 호출 방식 | Skill tool | Agent tool |
| 도구 접근 | 부모와 동일 | frontmatter로 제한 가능 |

**스킬로 해야 할 때**:
- 부모 컨텍스트의 정보가 필요한 작업
- 판단 기준이나 가이드라인을 제공하는 경우
- 현재 대화 흐름 안에서 처리해야 하는 경우

**에이전트로 해야 할 때**:
- 독립적으로 실행 가능한 작업
- 컨텍스트 분리가 필요한 경우
- 병렬 실행이 필요한 경우
- 다른 모델(haiku 등)을 사용하고 싶은 경우

## 10. 스킬과 에이전트 연결 방식

### 10.1 스킬이 에이전트를 호출

가장 일반적인 패턴. 스킬이 Orchestrator 역할을 하며 에이전트에 작업을 위임한다.

```
skill (orchestrator)
    |
    +-- Agent(subagent_type="researcher", prompt="...")
    +-- Agent(subagent_type="reviewer", prompt="...")
```

### 10.2 에이전트가 스킬을 참조

에이전트 정의 본문에서 스킬의 레퍼런스 파일을 참조하도록 지시한다. 에이전트가 Skill tool을 호출해 가이드를 로드한 뒤 작업을 수행한다.

```markdown
# agents/writer.md
---
allowed_tools:
  - Skill
  - Write
  - Read
---
작업 전에 반드시 `writing-style` 스킬을 로드하여 스타일 가이드를 확인하라.
```

### 10.3 스킬 체이닝

한 스킬이 다른 스킬을 로드하여 복합 가이드를 구성한다. 이 경우 에이전트 없이 스킬 간 연결만으로 워크플로우를 구성할 수 있다.

```
skill A (트리거) --> skill B 로드 (레퍼런스) --> 작업 수행
```

### 10.4 연결 시 주의사항

- 순환 참조를 피한다 (스킬 A -> 에이전트 -> 스킬 A)
- 에이전트 프롬프트에는 스킬의 핵심 내용을 직접 포함하는 것이 스킬 로드보다 효율적일 수 있다
- 에이전트가 스킬을 로드하면 그만큼 컨텍스트를 소비한다는 점을 고려한다
