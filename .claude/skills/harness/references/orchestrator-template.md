# 오케스트레이터 스킬 템플릿

## 작성 원칙

1. **Phase 0 필수**: 모든 오케스트레이터는 작업 시작 전 컨텍스트를 확인한다.
2. **데이터 흐름 명시**: 에이전트 간 데이터가 어떤 형식으로 오가는지 정의한다.
3. **실패 처리 내장**: 에이전트 실패 시 대응 방안을 포함한다.
4. **테스트 시나리오 포함**: 스킬이 올바르게 동작하는지 확인할 수 있는 시나리오를 제공한다.
5. **description은 트리거**: description이 스킬의 진입점이다. 정확한 트리거 조건을 명시한다.

### description 후속 키워드 작성법

description의 첫 문장은 "이 스킬이 무엇을 하는가"를 10단어 이내로 요약한다. 그 뒤에 트리거 키워드를 나열한다.

```yaml
description: |
  다중 소스 리서치를 병렬로 수행하고 결과를 종합한다.
  - When the user asks to research a topic from multiple sources
  - "리서치", "조사", "research", "investigate"
  - When a deep-dive across 3+ sources is needed
```

**pushy 작성법**: 모델이 이 스킬을 적극적으로 선택하도록 만드는 기법.

```yaml
# 약한 트리거 (모델이 무시할 수 있음)
description: "코드 리뷰에 사용할 수 있는 스킬"

# 강한 트리거 (pushy)
description: |
  코드 변경사항을 리뷰한다.
  MUST use this skill whenever the user asks for code review,
  diff review, PR review, or says "review".
  Use BEFORE writing any review comments.
```

## 템플릿 A: 에이전트 팀 모드

에이전트 간 직접 통신이 필요한 경우 사용한다. 토론, 피드백 교환, 반복 협업에 적합하다.

```markdown
---
description: |
  [스킬 설명 1줄]
  - [트리거 조건 1]
  - [트리거 조건 2]
---

# [오케스트레이터 이름]

## Phase 0: 컨텍스트 확인

작업 시작 전 다음을 확인한다:

1. 사용자 요청에서 작업 범위를 추출한다
2. 필요한 입력 데이터가 존재하는지 확인한다
3. 작업 환경(파일 구조, 의존성)을 점검한다

확인 실패 시: 사용자에게 부족한 정보를 요청하고 중단한다.

## Phase 1: 팀 구성

TeamCreate로 에이전트를 생성한다.

### Agent A: [역할명]
- **역할**: [구체적 역할 설명]
- **입력**: [받는 데이터 형식]
- **출력**: [반환 데이터 형식]

### Agent B: [역할명]
- **역할**: [구체적 역할 설명]
- **입력**: [받는 데이터 형식]
- **출력**: [반환 데이터 형식]

## Phase 2: 작업 지시

SendMessage로 각 에이전트에 작업을 지시한다.

### Agent A에게:
```
[작업 지시 프롬프트 템플릿]
입력 데이터: {data}
출력 형식: JSON으로 다음 필드를 포함
- field_1: 설명
- field_2: 설명
```

### Agent B에게:
```
[작업 지시 프롬프트 템플릿]
```

## Phase 3: 협업 (선택)

에이전트 간 직접 통신이 필요한 경우:
- Agent A의 결과를 Agent B에게 SendMessage로 전달
- Agent B의 피드백을 Agent A에게 전달
- 합의에 도달하면 다음 Phase로 진행

최대 교환 횟수: [N]회. 초과 시 Orchestrator가 판단하여 결정.

## Phase 4: 결과 종합

모든 에이전트의 결과를 수집하여 최종 산출물을 구성한다.

### 종합 기준:
- [기준 1]
- [기준 2]

### 최종 출력 형식:
```json
{
  "summary": "종합 요약",
  "details": [...],
  "metadata": { "agents_used": N, "total_time": "..." }
}
```

## 에러 처리

| 상황 | 대응 |
|------|------|
| 에이전트 응답 없음 | 30초 대기 후 재시도. 2회 실패 시 해당 에이전트 없이 진행 |
| 에이전트 결과 형식 오류 | 형식 재지시 후 1회 재시도 |
| 전체 실패 | 사용자에게 실패 사유 보고 |

## 테스트 시나리오

### 시나리오 1: 정상 흐름
- 입력: [테스트 입력]
- 기대: [기대 결과]

### 시나리오 2: 부분 실패
- 입력: [테스트 입력]
- 에이전트 1개 실패 조건
- 기대: 나머지 결과로 종합 가능

### 시나리오 3: 빈 입력
- 입력: 없음
- 기대: Phase 0에서 중단, 사용자에게 안내
```

## 템플릿 B: 서브 에이전트 모드

에이전트 간 통신이 불필요하고 독립 작업을 위임하는 경우 사용한다.

```markdown
---
description: |
  [스킬 설명 1줄]
  - [트리거 조건 1]
  - [트리거 조건 2]
---

# [오케스트레이터 이름]

## Phase 0: 컨텍스트 확인

작업 시작 전 다음을 확인한다:

1. 사용자 요청 파싱: 무엇을, 어떤 범위로, 어떤 기준으로
2. 입력 데이터 존재 확인
3. 출력 위치/형식 확인

확인 실패 시 중단하고 사용자에게 질문한다.

## Phase 1: 작업 분할

사용자 요청을 N개의 독립 작업으로 분할한다.

### 분할 기준:
- [기준 1: 예) 파일별, 모듈별, 주제별]
- [기준 2]

### 각 작업의 스펙:
```json
{
  "task_id": "task_N",
  "input": "해당 작업의 입력",
  "constraints": "제약 조건",
  "expected_output": "기대 출력 형식"
}
```

## Phase 2: 병렬 실행

각 작업을 서브 에이전트에 위임한다. 독립 작업이므로 `run_in_background: true`로 병렬 실행한다.

### 에이전트 호출 템플릿:

```
Agent(
    description="[3-5단어 작업 요약]",
    subagent_type="[에이전트 타입]",
    prompt="""
    ## 작업
    [구체적 작업 지시]

    ## 입력
    {task_input}

    ## 출력 형식
    다음 형식으로 결과를 반환하라:
    - [필드 1]: [설명]
    - [필드 2]: [설명]

    ## 제약
    - [제약 1]
    - [제약 2]
    """,
    run_in_background=True
)
```

**중요**: 서브 에이전트 프롬프트는 자기 완결적이어야 한다. 부모 대화의 컨텍스트를 모르는 상태에서 시작하므로 필요한 모든 정보를 프롬프트에 포함한다.

## Phase 3: 결과 수집 및 종합

모든 에이전트 완료 후 결과를 종합한다.

### 종합 전략:
- **병합**: 결과를 단순 합침 (리스트 연결)
- **비교**: 결과 간 차이점/공통점 분석
- **선택**: 최고 품질의 결과 선택
- **변환**: 결과를 새로운 형식으로 재구성

### 최종 출력:
[출력 형식 정의]

## 에러 처리

| 상황 | 대응 |
|------|------|
| 에이전트 타임아웃 | 해당 작업 건너뛰고 결과에 표시 |
| 결과 형식 불일치 | 부분 파싱 시도. 실패 시 건너뜀 |
| 모든 에이전트 실패 | Orchestrator가 직접 축소 실행 |

## 테스트 시나리오

### 시나리오 1: 정상 (3개 작업)
- 입력: [구체적 테스트 입력]
- 기대: 3개 결과 종합

### 시나리오 2: 단일 작업
- 입력: 분할 불가능한 단일 요청
- 기대: 에이전트 1개만 실행

### 시나리오 3: 대규모 (10개 이상)
- 입력: 대량 작업
- 기대: 배치 분할하여 처리 (동시 최대 5개)
```

## 템플릿 C: 하이브리드 모드

파이프라인의 일부 단계에서 팬아웃이 필요하거나, 팀 모드와 서브 에이전트 모드를 혼합하는 경우 사용한다.

```markdown
---
description: |
  [스킬 설명 1줄]
  - [트리거 조건 1]
  - [트리거 조건 2]
---

# [오케스트레이터 이름]

## Phase 0: 컨텍스트 확인

1. 사용자 요청에서 작업 유형을 판별한다
2. 작업 규모를 추정한다 (소/중/대)
3. 필요 리소스를 확인한다

규모별 전략 선택:
- **소**: 서브 에이전트 1개로 처리
- **중**: 파이프라인 + 팬아웃
- **대**: 팀 모드 + 감독자

## Phase 1: 준비 단계 (파이프라인)

순차적으로 실행해야 하는 전처리 작업.

```
Agent(prompt="Step 1: 입력 데이터 분석 및 작업 계획 수립...")
--> 작업 계획 (JSON)
```

## Phase 2: 병렬 실행 단계 (팬아웃)

Phase 1의 계획에 따라 작업을 병렬 분배.

```
# Phase 1 결과에서 작업 목록 추출
tasks = parse_plan(phase1_result)

# 병렬 실행
for task in tasks:
    Agent(
        prompt=f"작업: {task}",
        run_in_background=True
    )
```

## Phase 3: 검증 단계 (팀 모드, 선택)

병렬 결과에 대해 검증이 필요한 경우 팀 모드로 전환.

```
# Reviewer 에이전트 생성
TeamCreate(reviewer)
TeamCreate(author)

# 결과를 Reviewer에게 전달
SendMessage(reviewer, "다음 결과를 검증하라: {results}")

# Reviewer 피드백을 Author에게 전달
SendMessage(author, "피드백 반영: {feedback}")
```

## Phase 4: 최종 종합

모든 단계의 결과를 종합하여 최종 산출물을 생성한다.

### 데이터 흐름 요약:
```
[입력] --> Phase 1 (순차) --> Phase 2 (병렬) --> Phase 3 (팀) --> [최종 출력]
```

## 에러 처리

| Phase | 상황 | 대응 |
|-------|------|------|
| 1 | 계획 수립 실패 | 단순 분할로 폴백 |
| 2 | 일부 에이전트 실패 | 실패 작업만 재실행 |
| 3 | 검증 합의 실패 | 최대 3라운드 후 다수결 |
| 4 | 종합 실패 | 부분 결과라도 반환 |

## 테스트 시나리오

### 시나리오 1: 소규모 (서브 에이전트만)
- 기대: Phase 1 -> Phase 2 (1개) -> Phase 4

### 시나리오 2: 중규모 (파이프라인+팬아웃)
- 기대: Phase 1 -> Phase 2 (3-5개) -> Phase 4

### 시나리오 3: 대규모 (전체 흐름)
- 기대: Phase 1 -> Phase 2 (5개+) -> Phase 3 -> Phase 4

### 시나리오 4: 팬아웃 부분 실패
- 기대: 실패 작업 재시도 후 부분 결과로 진행
```

## 공통 패턴: Phase 0 컨텍스트 확인 상세

모든 템플릿에서 Phase 0는 다음 3단계로 구성한다.

### 단계 1: 요청 파싱

사용자의 자연어 요청에서 구조화된 작업 스펙을 추출한다.

```
요청: "React 프로젝트의 컴포넌트들을 리뷰해줘"

파싱 결과:
- 작업 유형: 코드 리뷰
- 대상: React 컴포넌트
- 범위: 프로젝트 전체
- 기준: 명시되지 않음 (기본값 사용)
```

### 단계 2: 환경 검증

작업 수행에 필요한 환경이 갖춰져 있는지 확인한다.

```
- 대상 파일이 존재하는가?
- 필요한 도구에 접근 가능한가?
- 작업 결과를 저장할 위치가 있는가?
```

### 단계 3: 전략 결정

환경과 요청에 따라 실행 전략을 결정한다.

```
- 에이전트 수: 대상 규모에 비례
- 실행 모드: 작업 특성에 따라 선택
- 타임아웃: 작업 복잡도에 따라 조정
```
